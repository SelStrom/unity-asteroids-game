# DESISIONS.md — Фича «Самонаводящиеся ракеты»

Ветка: `feature/rockets-pure-fable5-med` · Дата: 2026-06-09 · Модель: Claude Fable 5 (medium)

## Исходный промт

> **Сомонаводящиеся ракеты.** Нужно сделать новую фичу. Добавим самонаводящиеся ракеты. У игрока есть одна ракета, которую можно запустить, нажав кнопку R. Ракета летит по дуге в ближайшую цель. Если ракета по пути врежется не в выбранную цель, это тоже считается. После запуска ракет включается счётчик на респавн ракет. Количество ракет у игрока и время респавна должно быть задано в конфигах. Ракета коллайдится с астероидами и UFO. В качестве визала ракеты можно использовать уменьшенный спрайт корабля. Инверсионный след можно сделать из спрайта частиц. Ракета должна быть создана и вписана в текущую архитектуру ECS + визуал. Количество доступных ракет и время респавна должно выводиться в HUD-е игрока. Фича должна быть разработана в парадигме TDD, весь функционал покрыт тестами. Проверка функционала при помощи юнит, интеграционных тестов и MCP. Human validation в исключительных случаях, когда текущих инструментов недостаточно и невозможно написать новый функционал для MCP.

## Ключевые решения

### Архитектура

1. **Реальная архитектура — гибридный DOTS, а не описанный в CLAUDE.md MonoBehaviour-ECS.**
   Разведка показала: логика живёт в `Assets/Scripts/ECS/` (Unity Entities 1.4.5, `ISystem`,
   `IComponentData`), мост к MVVM-визуалу — в `Assets/Scripts/Bridge/`. Фича вписана именно
   в этот стек.

2. **Ракета несёт `PlayerBulletTag` + собственный `RocketTag`.**
   Требование «врезалась не в выбранную цель — тоже считается» получено бесплатно:
   существующий `EcsCollisionHandlerSystem` обрабатывает пару PlayerBullet+Enemy
   (оба умирают, очки начисляются) без единой новой ветки кода. `RocketTag` отделяет
   ракету для системы наведения и каталога. Тесты `RocketCollisionTests` прошли сразу
   после RED-фазы — подтверждение корректности переиспользования.

3. **Боезапас — `RocketAmmoData` на корабле, зеркало `LaserData`.**
   `CurrentRockets` / `RespawnRemaining` / `Launching` — та же схема, что у лазера
   (`EcsRocketLaunchSystem` — структурная копия `EcsLaserSystem`). Таймер респавна
   тикает только при неполном боезапасе. Конфиг: `MaxRockets`, `RespawnDurationSec`
   в `GameData.Rocket` (требование «из конфигов»).

4. **Самонаведение «по дуге» = ограниченная угловая скорость доворота.**
   `EcsRocketHomingSystem`: кратчайший знаковый угол до цели, клампится
   `TurnSpeedDegPerSec * deltaTime` → траектория-дуга. Цель — ближайший живой враг
   (Asteroid/Ufo/UfoBig без `DeadTag`); при смерти/уничтожении цели — автоматический
   ретаргет. Захваченная цель хранится в `RocketData.TargetEntity` (не пересчитывается
   каждый кадр — «летит в ближайшую цель», выбранную при захвате).

5. **Поворот визуала — через `RotateData`.**
   Ракета получает `RotateData.Rotation = Direction`; существующий `GameObjectSyncSystem`
   уже умеет синхронизировать позицию+поворот для entity с `MoveData`+`RotateData`.
   Ноль нового кода синхронизации.

6. **Время жизни — переиспользование `LifeTimeData`.**
   `EcsLifeTimeSystem`/`EcsDeadByLifeTimeSystem` гасят ракету без цели за `LifeTimeSeconds` (10 c).

7. **Спавн — событийный, как у пуль.** `RocketLaunchEvent` (buffer-синглтон, создаётся в
   `Application.InitializeEcsSingletons`, чистится при рестарте в `Game.ClearEcsEventBuffers`)
   → `ShootEventProcessorSystem.ProcessRocketEvents` → `EntitiesCatalog.CreateRocket`.

8. **Визуал — префаб-копия `bullet.prefab` с компонентом `BulletVisual`.**
   Отдельный `RocketVisual` не создавался: поведение View идентично пуле
   (репорт коллизии в `CollisionBridge`), различия только в данных префаба.
   Спрайт — тот же sub-asset атласа, что `Ship.MainSprite` (fileID 2092087282),
   масштаб 0.5 («уменьшенный спрайт корабля»). Инверсионный след — child
   `ParticleSystem`: эмиссия `rateOverDistance` в world space (частицы остаются
   позади по траектории — естественный contrail без возни с направлением выхлопа).

9. **Ввод — действие `Rocket` (клавиша R)** в `player_actions.inputactions`
   (обёртка `PlayerActions.cs` перегенерирована Unity автоматически,
   `generateWrapperCode: 1`) → `PlayerInput.OnRocketAction` → `Game.OnRocket`
   выставляет `Launching/Direction/LaunchPosition` — точная копия пути лазера.

10. **HUD — расширение существующего конвейера.** `HudData.RocketCount` /
    `RocketRespawnTime` / `IsRocketRespawnTimeVisible` → `ObservableBridgeSystem`
    (запрос по кораблю расширен `RocketAmmoData`) → два TMP-текста в `Main.unity`,
    клонированные из лазерных строк (стиль/шрифт/позиционирование консистентны).
    Таймер респавна скрывается при полном боезапасе — как у лазера.

### Параметры конфига (GameData.asset)

| Параметр | Значение | Обоснование |
|---|---|---|
| MaxRockets | 1 | «У игрока есть одна ракета» |
| RespawnDurationSec | 15 | Ракета мощнее лазера (самонаводится) — кулдаун дольше лазерного (10 c) |
| Speed | 8 | Быстрее врагов (1–3) и корабля (max 15 достижим редко), медленнее пули (20) — дуга читается глазом |
| TurnSpeedDegPerSec | 150 | Уверенный перехват без «прилипания»; дуга видна |
| LifeTimeSeconds | 10 | Гарантированная смерть ракеты без целей |

### Процесс (TDD)

- **RED → GREEN на уровне циклов:** (1) launch/ammo + homing + коллизии — 12 падающих
  тестов до реализации, затем реализация; (2) фабрика — RED через ошибки компиляции
  нового API, затем реализация. Скелеты систем с пустым `OnUpdate` написаны до тестов,
  чтобы RED был именно падением ассертов, а не случайным не-компилом.
- **Пост-хок интеграционные тесты** (PlayMode) — по принципам проекта: проверяют цепочку
  спавна в default world и самонаведение в player loop.
- Итог: **190 EditMode + 9 PlayMode, все зелёные.** Новых тестов: 25
  (7 launch, 9 homing, 3 collision, 4 factory, 2 HUD-bridge, 2 PlayMode-интеграция),
  плюс хелперы фикстуры.

### Верификация через MCP (без human validation)

Human validation не понадобилась — хватило MCP:

1. `tests-run` EditMode/PlayMode — все прогоны RED/GREEN.
2. `script-execute` (Roslyn) — функциональный сценарий в живом playmode: старт игры
   кнопкой титульного экрана, запуск ракеты (эквивалент R — установка `Launching`,
   как делает `Game.OnRocket`), пошаговая прокрутка кадров `EditorApplication.Step()`
   на паузе (обход проблемы «кадры не тикают в расфокусированном редакторе»).
   Подтверждено: расход боезапаса 1→0, тикающий таймер, захват цели, доворот
   направления, живой визуал с частицами следа, попадание (очки 0→2), HUD-строки.
3. `screenshot-camera` — визуально: ракета (уменьшенный корабль) с дуговым
   инверсионным следом, HUD «Rockets: 0» / «Respawn rocket: 13 sec».
   (`screenshot-game-view` на паузе отдаёт устаревшую/перевёрнутую текстуру —
   снимали напрямую с Main Camera.)
4. `console-get-logs` — ноль ошибок/исключений в рантайме.
5. Ассеты созданы через MCP: `assets-copy` (префаб), `script-execute` +
   `EditPrefabContentsScope` (спрайт по точному fileID sub-asset'а, масштаб,
   ParticleSystem), правка сцены через `SerializedObject` с сохранением.

### Отклонения и нюансы

- **Прямые YAML-правки** `GameData.asset` (блок Rocket) и `player_actions.inputactions`
  (JSON): формат детерминированный, точечная правка надёжнее reflection-сериализации
  MCP для sub-asset-ссылок c fileID. Все изменения провалидированы рефрешем,
  тестами и живым playmode.
- Симуляция нажатия R в playmode сделана установкой `RocketAmmoData.Launching`
  (байт-в-байт то, что делает `Game.OnRocket`); сам путь клавиша→событие покрыт
  кодогенерацией Input System и тривиальной подпиской — отдельно не эмулировался.
- GSD/superpowers не использовались (явное требование промта, override CLAUDE.md).

## Оценка по токенам

Приблизительно (суммарно за сессию, одна беседа без подзадач кроме одного
Explore-агента на разведку):

| Статья | Оценка |
|---|---|
| Входные токены (с учётом перечитывания контекста между ходами, ~55 ходов) | ~1.5–2.5 млн кэшированных + ~150–250 тыс. свежих |
| Выходные токены (код, тесты, MCP-скрипты, текст) | ~40–55 тыс. |
| Explore-субагент (разведка архитектуры) | ~100–150 тыс. вход / ~5 тыс. выход |

Основные расходы: чтение ~20 файлов кодовой базы, 6 циклов компиляции/тестов Unity,
5 Roslyn-скриптов верификации, 3 скриншота. Экономия достигнута батчингом правок
(один refresh на цикл) и переиспользованием существующих систем вместо новых.
